## 结论

不建议在现状上再加一套独立的“全项目 Prompt 审计系统”。建议先把已有的来源解析、生效状态、归属与编辑语义收拢到一个 Prompt 领域边界，再让单页读取、网页草稿、生成编译和项目检查消费它。

不是把所有读写塞进一个文件，也不是把所有 JSON 合并：保留现有事实拆分、模型适配器和共享词稳定 ID。统一的是对这些事实的解释与修改责任。

近期推荐：**不迁移存储，先统一领域视图和编辑流程**。项目检查只是同一视图的分页筛选。按角色嵌套保存词条是可讨论的后续选择，不作为第一步前提。

## 1. 当前事实究竟放在哪里

| 事实 | 当前位置 | 实际含义 |
| --- | --- | --- |
| 页面归属 | `pages/index.json` | 属于某单元、角色或场景的哪个位置；不等于画面引用 |
| 画面角色引用 | `pages/<id>.content.json` 的 `characters` | 当前画面参与者及所用子设定；不是对白说话人列表 |
| 对白 | 同文件 `dialogue` | 允许画外角色说话；不能据此自动添加画面角色 |
| 活动模型与画幅 | `pages/<id>.render.json` | 决定活动模型分支；另一模型分支仍可保留 |
| 本页 Prompt | `pages/<id>.prompt.json` 的 `models.<model>` | Anima 的分类词、场景引用、本层覆盖与 LoRA；Qwen 是不同的文字／参考图契约 |
| 角色／场景基础与子设定 | 各自 `.prompt.json` 中的 `identity`、`variants` | 上游共享词、子设定追加词与对基础的调整 |
| 子设定声明 | 各自 `.visual.json` | 子设定身份和名称，不能只凭 Prompt 中有同名键认定引用有效 |
| 最终生成输入 | 读取上述事实后编译；任务提交时冻结 | 派生值，不应作为另一份可编辑事实保存 |

Anima 中，一个本页词可以有 `character_id`，也可以没有。**分类与归属是两条独立轴**：`person` 表示人物相关，不代表已绑定某个角色。人数控制也不代表角色引用。

共享词有稳定 ID，是为了上游改字、排序以后，下游逐词开关／权重仍跟随同一项。本页词没有持久 ID，数组表达顺序。这个区别有现实价值，不能统一删除 ID。

例如：页面人数为一人、本页只写甲的动作，同时 `content.characters` 仍有甲乙两人，乙的共享词就仍会生效。删除乙的本页词或显式 LoRA，并不等价于解除乙的引用。

## 3. 深层原因

### 3.1 文件范围被误当成用户操作范围

物理文件拆开合理，但“调整这一页的视觉 Prompt”自然包括画面角色、场景引用、本页追加词、继承开关。旧接口让调用者先理解哪个字段藏在哪个文件，再协调多次读写。用户说“删掉乙”，Agent 却容易只删除它眼前的 `person` 行。

### 3.2 类别与归属没有同等可见性

页面词按类别平铺，绑定是可选字段；最容易生成的输入也是不带角色的平铺数组。新增继承展示缓解了“看不见”，但还没有让“在哪个角色下新增词”成为最自然的写法。

未绑定并非一概错误：共同关系、匿名人物等需要它。不能强制所有 `person` 词绑定，也不能仅凭词典或历史频率自动猜角色。

### 3.3 缺少统一的、可追溯的有效视图

原始事实、有效词、最终字符串是不同层次。目前有共享的小函数，却没有一个被各消费者共同采用的领域结果。调用者仍需自行选择来源、应用多层覆盖、理解极性和归属、判定重复。临时脚本就是这个缺口的外显。

### 3.4 批量计划和读据脱节

本次 `assemble.mjs` 从新 read 回执提取指纹，但 `changes.person` 来自此前独立生成的数组。指纹保护的是新读取的事实，替换正文却来自旧计划。即使当前没有并发编辑，也不应把这种路径作为标准用法。

不必再加租约或草稿数据库；只须让修改基于同一份读取正文构造。跨轮保存计划要保留原读据，过期后重新判断，不能领取新指纹给旧数组“续期”。

这是标准操作流程的约束，不是 SHA 接口能识别的客户端意图：任意调用者仍能把旧数组配上新指纹。服务端能验证事实版本与结构，不能证明数组来自哪一次思考。本方案不为此增加持久草稿平台或承诺不可能的检测能力。

### 3.5 “重复”实际上存在不同政策

审核确认当前至少有三种路径：shared 的 `duplicatePromptWords` 按归属和极性检查，其中 `setting/camera` 统一归环境，比较不含权重；Anima 编译器的 `deduplicateCompiledParts` 按极性、scope、文本抑制后项，也不比较类别和权重；最近 `prompt-scope` 的提示仅比较本页 person 与角色继承词。

这些不是换个函数名就能合并的相同规则。需要统一数据和诊断定义，同时保留“提示可能重复”“阻断生成”“编译抑制后项”的不同后果。第一阶段固定当前编译输出，不顺便调整去重政策。

## 4. 推荐结构：一个领域解释，多个轻重不同的投影

```text
现有拆分事实 + 必要来源
          ↓
统一 Prompt 领域解析（按模型实现，纯计算部分可在浏览器复用）
          ├─ 单页编辑：本层正文 + 角色/场景归属 + 必要继承
          ├─ 网页草稿：同样的来源、开关、计数与诊断
          ├─ 项目检查：只返回问题摘要和定位
          └─ 生成编译：按模型/配置规定的顺序序列化并冻结
```

建议分清两个实质职责，不建立多层空包装：

1. **加载事实**：由服务端读取本页活动模型、实际引用和所需基础／子设定；记录依赖与缺失来源。请求内共享来源只读一次，不增加长期缓存、数据库或缓存失效系统。
2. **解释事实**：在现有 shared/model 边界内统一应用基础 → 子设定 → 页面覆盖，给出有效内容、来源和诊断。网页用同样计算解释未保存草稿；服务端是最终保存与生成的校验方。

有效项应能回答：来自哪里、属于谁、正向还是负向、当前开关和权重是什么、覆盖在哪一层、要编辑哪个事实。共享项定位使用现有稳定键；本页项使用当前读据下的类别与位置，不引入新持久 UUID。

解析结果保留全部原始项及其来源，不在读取阶段提前删重。最终编译若抑制某项，应记录采纳／抑制状态和原因，供同一领域的详细诊断投影使用；日常窄读取不必回传完整编译 trace。统一诊断事实与严重性映射，不把当前任一去重函数直接升级为所有用途的规则源。

“有效领域视图”不等于“最终发送给模型的字符串”：全局配置、触发词、类别顺序、模型格式和参考图编号仍由编译层负责。检查与编译共享事实语义，不能把编译器已计算的继承留着，再在审计里重算一遍。

Qwen 保留整段覆盖和 standalone，不生搬硬套 Anima 的逐词体系。standalone 可以仍存在页面角色元数据，但其上游不参与生成；视图必须明确这个区别。LoRA 来源需要可追溯，但不趁此重构训练系统或改变用户的 LoRA 审批规则。

还须区分“保存着”“开关启用”“会进入最终生成”三个状态。例如 Anima 场景当前只编译 `setting/avoid`，不能把场景其他分类的启用项都说成有效输入。Qwen 的可用参考图库与实际选择的图片 ID 也不是一回事；未覆盖时的默认选择、显式空选择、页面覆盖和最后的图片顺序应保留各自含义。统一视图提供这些状态，不把所有模型揉成同一种词条。

## 5. 写入如何变得自然

页面视觉编辑应在一个领域边界内表达：当前画面角色／子设定、场景引用、当前模型本页词及覆盖。可以继续分文件保存，由同一操作负责必要字段的原子更新与清理，而不是让 Agent 自己先存 content 再猜要清哪些 Prompt 键。

推荐优先复用现有页面整体保存事务与 `prompt.read/save` 的窄范围能力，收拢其领域实现。最终工具名和 JSON 参数在实施时决定，不并列增加“旧版编辑”“新版编辑”“审计专用编辑”三套长期入口。

统一编辑边界不意味着每次必须读写整页或所有模型。只改某角色的本页词，仍按相关范围读取、修改；修改跨模型共用的角色引用时，提交边界才须覆盖引用及清理会触及的各模型事实。服务端校验这些必要依赖，不能用活动分支的旧凭证顺便覆盖另一分支新改动。沿用现有短事务与指纹，不增加全项目长锁。

绑定操作应具有明确目标：在甲的本页词区域新增／替换时，归属由区域提供，不要求每一项重复填写 `character_id`；共同／未绑定区域独立可见。它可以只是现有平铺存储的编辑投影，不必同时维护一份嵌套事实。投影必须保留原数组顺序，不能因为按角色展示就静默重排最终输出。

解除引用的统一规则：

- 删除确实被解除角色的绑定本页词和对应引用覆盖；从当前引用解析时自然不再继承该角色的词与 LoRA。
- 同一角色切换子设定时保留角色绑定的本页词，清理旧子设定来源的覆盖。
- 若画面角色引用仍跨模型共用，解除角色要对所有受影响模型的依赖字段作一致清理，不能只处理活动分支；清理与用户编辑同一次提交。
- 保留画外对白；不通过删除对白来修复视觉引用。
- 未绑定自由文字、共同关系词、显式页面 LoRA 不能凭相似名字自动删除；返回具体待核对项，而不是声称“全部干净”。
- 网页本地草稿预览与服务端保存执行同样的确定性变换。

LoRA 还有一个必须补齐的具体边界：[lora-config](../../app/server/lora-config.mjs) 中 `trigger_sources.characters/scenes` 仍保存来源位置，`lora_overrides` 则按 filename 共用。当前角色清理 helper 没有处理它们；失联角色的旧触发词来源可能让保留的显式 LoRA 触发词被风格段排除。因此应清理明确解除的角色触发词来源，并从剩余角色、场景、项目风格和显式页面定义共同判断覆盖是否失去全部来源，不能按被删除角色的 filename 一刀切。保留显式 LoRA 时，其触发词归属应重新解析；权重和模型定义不擅自修改。此项是引用生命周期完整性，不是推荐 LoRA 用法。

建议悬空覆盖规则：只针对本次解除来源所涉及的 filename，确认在该模型所有剩余有效来源及显式定义中均不存在时清除覆盖；仍有任一来源则保留。来源缺失导致无法判断时保留并报告，不顺便清空其他历史覆盖。按这条规则更新依赖指纹，不以读取另一模型的当前数据绕过并发保护。

## 6. 第一项“全项目检查”具体怎样落地

它是上面领域视图的批量查询方式，而非新的规则源。支持项目／章节／单元范围，逐页按实际活动模型解析；明确标注未扫描的非活动分支。需要检查某指定模型时显式选择。

页面枚举使用正式页面索引和归属顺序，不递归扫描整个项目目录，不混入备份、历史输出或未登记文件。目录归属只用于选择检查范围，不能因此隐式添加角色或场景引用。

默认只给：已扫描／无法解析数量、按问题类型的计数、少量页面样例、继续读取位置。详情按页返回该问题的本地位置、对应来源和原因。不能静默截断后报告“全项目通过”。范围内单页缺失来源时报告该页不可判定，继续检查其他页，不凭空补来源。

分页期间允许项目变化，不引入长时间全项目锁；摘要是观察结果，不是修改凭证。处理某页时重新取得该页领域读据，并在这份正文上形成修改。单次页面读取仍使用既有一致性边界，不能混合前后版本的来源。

检查分成两类，避免把猜测当作错误：

| 确定事实／结构问题 | 只供判断的提示 |
| --- | --- |
| 来源不存在、绑定指向未引用角色、非法覆盖键 | 未绑定人物词，不代表一定应绑定 |
| 同归属、同极性、同生效文本确实重复的事实（不等于安全可删） | 未绑定词与某角色继承词相同，可能在强调另一人 |
| 来源被关闭、某引用没有本页追加词等客观状态 | 多人共享同一属性、自由描述语义相似 |

即使是确定的文本重复，也不能忽略权重、有效开关、类别及模型顺序，更不能自动把两个角色相同的词合为一个。检查先提供证据，不默认执行清理。`night` 与 `at night` 等语义近似不引入 LLM 或模糊规则判断。

修改仍走原领域保存能力。大量机械修改可落盘草稿和回执，但摘要不要把整项目正文灌入上下文；语义归属仍由 Agent 在获授权范围内判断。

## 7. 存储是否应按角色重组

**方案 A（推荐现在做）：保持存储，改变领域边界与编辑投影。**

收益：无需迁移核心项目，已有 UUID/逐词继承继续可靠，能直接替换多处重复解释。风险：如果仅套一层新接口、内部仍保留各自解析，就没有真正收敛。必须以移除重复实现作为完成条件。

**方案 B：持久化改为人物／场景分组，本页词嵌在归属下。**

好处是“归属”成为数据容器的固有属性，少填错 ID；但要同时决定人物引用是否从 content 移出、不同模型是否共享参与者、共同关系词放哪里、全局顺序如何保持。若还同时保留 `content.characters` 和新角色容器，两者就是重复事实，问题会更严重。

只有明确希望不同模型具有不同的画面参与者，或方案 A 实际仍经常发生归属错误时，才值得做 B。不能把当前跨文件组织当作必须重写整个项目格式的充分理由。直接扁平化所有继承成一份本页全文不采用：那会丢失用户要求的逐词跟随上游。

## 8. 如何控制复杂度与验证成本

按一条竖向路径推进：先一页 Anima 的读取、网页草稿、编译一致；再接入现有批量读取；最后提供项目检查视图。模型差异通过现有适配器处理，不做可配置的通用规则平台。

明确替换／收回的内容：

- `prompt-scope` 新增的独立生效展示与重复匹配，改为消费共同领域结果；保留可读性，不保留第二套判断。
- `prompt-edit-context`、网页计数与编译中重复的引用选择／生效计算，逐步移到共同路径；各自保留必要投影和序列化。
- 前一轮新增的角色清理 helper 变成浏览器与服务端共享的引用变更语义，而不是继续在各入口补清理分支。
- 临时审计脚本只保留一次性证据，不纳入产品功能和长期文档。

轻量验收集中在容易复发的行为：两角色同词不误报为可删；三级开关和权重结果一致；移除／换子设定保留正确范围；共享 LoRA 覆盖和保留显式 LoRA 的触发词不会误清；画外对白不影响参与者；standalone 不假继承；批量详情与单页一致；标准批量脚本在同一读据的正文上计算修改；现有生成顺序、编译去重结果和冻结任务契约不变。做少量有意义的 fixture 与浏览器草稿回归，不做数百页逐项人工审批。不同权重同文本项至少保留一个明确的编译行为用例，不能以输出快照通过就宣称删除安全。

第一阶段不迁移项目。若最终选择 B，只迁移午夜甜点并顺带处理爱经；其他项目按用户确认忽略。不扩大为旧资产兼容框架。

## 9. 需要保留的决策与局限

建议默认维持“画面角色跨模型共用”；若用户想让 Anima/Qwen 的参与者不同，应另行明确，这会改变存储边界。
